项目的 RBAC 数据模型、种子数据、首管理员引导和授权工具已经就绪，但还没有角色管理 UI。当前采用粗粒度权限：只区分 `basic:manage` 和 `ai:manage`，主题配置和 dashboard 概览不限制。**新增页面/API 默认不校验权限，需要时再显式接入**。

- `UserRole` 和 `RolePermission` 使用复合主键，防止重复分配。
- 所有关联都使用 `onDelete: Cascade`。
- `Permission.name` 是稳定的授权标识，例如 `basic:manage`、`ai:manage`。
- `Permission.module` 用于按模块分组展示或筛选。

## 分配角色

目前可以通过 Prisma Studio、迁移种子脚本或自己的管理 API 分配角色。

```ts
await prisma.userRole.create({
  data: {
    userId,
    roleId,
  },
});
```

给角色添加权限：

```ts
await prisma.rolePermission.create({
  data: {
    roleId,
    permissionId,
  },
});
```

一次查询用户的全部权限：

```ts
const user = await prisma.user.findUnique({
  where: { id: userId },
  select: {
    roles: {
      select: {
        role: {
          select: {
            name: true,
            permissions: {
              select: {
                permission: {
                  select: { name: true },
                },
              },
            },
          },
        },
      },
    },
  },
});

const permissions = new Set(
  user?.roles.flatMap(({ role }) =>
    role.permissions.map(({ permission }) => permission.name),
  ) ?? [],
);
```

## 种子数据与首管理员

权限目录和内置角色由代码维护：权限常量定义在 `lib/permissions.ts`，通过幂等的 `prisma/seed.ts` 同步到数据库。

```bash
bun run db:seed     # 只同步权限和内置角色
bun run db:setup    # 生成客户端 + 迁移 + 同步（新环境推荐）
```

内置角色：

- `admin`：拥有 `PERMISSIONS` 中的全部权限。
- `user`：普通用户，默认无后台权限。

当前权限目录只有两个：

| 权限 | 覆盖范围 |
| --- | --- |
| `basic:manage` | 用户、角色、权限管理 |
| `ai:manage` | 模型、提供商、智能体、知识库管理 |

主题配置和 dashboard 概览不做权限限制。需要更细的粒度时，再往 `PERMISSIONS` 里增加常量即可。

内置角色被视为“代码拥有”的系统数据，每次 seed 都会把它们的权限对齐到代码；用户自建的角色不会被修改。seed 只 upsert 当前权限，不会删除后台手工创建的权限。

新环境还没有管理员时，在 `.env.<NODE_ENV>` 中配置：

```ini
BOOTSTRAP_ADMIN_EMAILS=admin@example.com,ops@example.com
```

这些已验证邮箱登录后会自动获得 `admin` 角色。系统里一旦存在管理员，该逻辑自动失效，不需要在代码或数据库里写死固定账号。

## 授权判断

不要在客户端根据按钮是否显示来判断权限；权限必须在服务端校验。统一入口在 `lib/authz.ts`。

### API

新 API 默认只要求登录，使用 `withAuth`：

```ts
import { NextResponse } from "next/server";
import { withAuth } from "@/lib/authz";

export const GET = withAuth(async (_request, _context, user) => {
  return NextResponse.json({ userId: user.id });
});
```

需要权限时使用 `withPermission`：

```ts
import { withPermission } from "@/lib/authz";
import { PERMISSIONS } from "@/lib/permissions";

export const POST = withPermission(
  PERMISSIONS.basicManage,
  async (_request, _context, user) => {
    // ...
  },
);
```

### 页面

页面默认不校验权限。需要限制时，在 Server Component 里调用：

```ts
import { requirePermission } from "@/lib/authz";
import { PERMISSIONS } from "@/lib/permissions";

await requirePermission(PERMISSIONS.aiManage);
```

当前页面暂未接入权限校验，所有已登录用户都可以访问；后续按需在具体页面加上面的调用。新增页面在没有加校验之前，默认就是无权限要求的。

## 建议补充的能力

- 管理 API：角色 CRUD、权限 CRUD、用户角色分配。
- 页面级权限接入：按需在基础系列和 AI 系列页面调用 `requirePermission`。
- 审计：记录谁给谁分配了什么角色。
- 缓存：权限查询可以按用户短时间缓存，但角色变更后必须失效。

<Callout type="warn" title="RBAC 不是登录">
RBAC 只回答“这个已登录用户能做什么”。它不能替代 Session 校验；受保护页面必须在 layout、Server Action 或 Route Handler 中调用 `requireUser()` / `getCurrentUser()`。
</Callout>

## 增量升级

1. 在需要限制的页面里调用 `requirePermission`（当前页面暂未接入）。
2. 再增加角色管理页面。
3. 如果角色会频繁变化，考虑增加权限缓存和失效机制。
4. 如果未来需要多租户，应在 `UserRole` 中加入 `tenantId` 或引入独立租户模型，并重新设计唯一约束。
