本项目同时支持两种身份入口：

- **邮箱 + 密码**：完全由本地数据库和 Session 管理。
- **Logto**：通过 OIDC 登录，再把 Logto 身份映射到本地 `User`。

两种入口最终都会落到同一张 `User` 表和同一套本地 Session 上。核心约束是：**一个邮箱只对应一个本地 User**。

## 两种登录方式

| 方式 | 入口 | 凭据 | 账号来源 |
| --- | --- | --- | --- |
| 邮箱密码 | `/login` 表单 | 邮箱 + bcrypt 密码哈希 | 本地注册 |
| Logto | `继续使用 Logto` 按钮 | Logto OIDC | Logto 回调时创建或合并 |

本地登录和 Logto 登录最终都会调用 `createSession(user.id)`，写入同一种 httpOnly Cookie。业务代码不需要区分用户最初从哪里登录。

## 账号绑定规则

Logto 回调通过 `lib/logto-user.ts` 将 claims 映射到本地用户：

1. 如果 Logto 返回**已验证邮箱**，使用该邮箱查找本地用户。
2. 找到本地用户时，更新 `name`、`avatarUrl`，保留本地 `passwordHash`，因此邮箱密码仍然可以继续登录。
3. 没找到时，创建一个新的本地用户。
4. 如果没有已验证邮箱，使用 `<logto-sub>@logto.local` 作为占位邮箱，避免把未验证邮箱和本地已有账号错误合并。

<Callout type="warn" title="只信任已验证邮箱">
未验证的 Logto 邮箱不能用于合并本地账号，否则攻击者可以在 Logto 填写他人邮箱并接管本地账号。当前实现只在 `email_verified === true` 时使用真实邮箱。
</Callout>

## 会话模型

本地 Session 采用不透明 token：

- 客户端只持有随机 token，保存在 httpOnly Cookie。
- 数据库只保存 `sha256(token)`，即 `Session.tokenHash`。
- 每次受保护请求由 `proxy.ts` 根据 token 哈希查询会话和用户。
- 会话过期或用户被禁用时，服务端会删除会话并拒绝访问。
- 登出会删除本地 Session，并清理 Logto SDK 的 Cookie。

## 当前边界

- 本地**验证码登录未启用**。项目没有邮件发送服务，因此移除了任意 6 位验证码都能登录的占位逻辑；验证码/无密码登录应通过 Logto 或后续专门的 OTP 实现。
- 没有邮箱验证流程。注册时填写的邮箱默认可信，生产环境建议增加验证邮件。
- RBAC 数据模型已经建立，但还没有角色管理 UI 和授权 API；授权判断需要业务代码自己实现，详见 [RBAC 权限](./rbac)。
- 没有登录频率限制、审计日志和 MFA。增量升级建议见[演进与扩展](./evolution)。
