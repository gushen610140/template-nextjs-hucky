## 为什么让浏览器直传

应用部署在公网托管平台，RustFS 在自建服务器上。如果让文件先上传到 Next.js 再转发，会带来三个成本：

1. 带宽翻倍（用户 → 应用 → 存储）。
2. 大文件受平台请求体上限和执行时长限制。
3. Server Action 默认只接受 1 MB 请求体。

因此上传走「服务端签名 + 浏览器直传」：

```text
浏览器                 Next.js                     RustFS
  │  createUpload        │                           │
  ├─────────────────────▶│  建 PENDING 记录            │
  │  uploadUrl           │  预签名 PUT                │
  │◀─────────────────────┤                           │
  │  PUT 文件本体（带进度）                            │
  ├─────────────────────────────────────────────────▶│
  │  completeUpload      │                           │
  ├─────────────────────▶│  HEAD 校验大小 / 类型        │
  │                      ├──────────────────────────▶│
  │                      │  置为 READY                │
  │◀─────────────────────┤                           │
```

Server Action 只传 JSON，不承载文件字节，因此不受请求体限制影响。

## 记录状态机

`FileObject.status` 有三个值：

```text
createUpload ──▶ PENDING ──completeUpload──▶ READY
                    │                         │
                    └──── 校验失败 ────────────┴──▶ DELETED
```

| 状态 | 含义 | 是否出现在列表 |
| --- | --- | --- |
| `PENDING` | 已签发上传地址，客户端尚未确认 | 否 |
| `READY` | 对象已存在并通过校验 | 是 |
| `DELETED` | 软删除，元数据保留 | 否 |

`completeUpload` 是幂等的：重复确认直接返回成功。确认时用 `HeadObject` 回查真实大小和 MIME，因为预签名 PUT 无法在存储侧限制 `Content-Length`。如果对象大小超过 200 MB，会删除对象并把记录置为 `DELETED`。

## 对象键与显示名

```text
{ownerId}/{yyyy}/{mm}/{uuid}-{sanitized-name}
```

- 前缀是文件属主 ID，天然按用户隔离。
- `uuid` 保证改名、重传不会互相覆盖。
- `sanitized-name` 只保留字母、数字、`._-`，中文等字符会被替换。

用户看到的文件名存在 `FileObject.name`，与对象键解耦。因此**重命名不需要移动对象**，只改一行元数据。

## 文件夹只是元数据

`FileFolder` 用 `parentId` 自关联成树，不映射到对象键前缀。移动文件只更新 `FileObject.folderId`，存储侧没有任何操作，所以拖拽是毫秒级的。

删除策略刻意不一致：

| 对象 | 策略 | 原因 |
| --- | --- | --- |
| 文件 | 软删除，保留记录 | 便于审计与后续回收站 |
| 文件夹 | 硬删除，文件先软删除 | 文件夹本身没有保留价值，避免空壳记录 |

删除文件夹时先用广度优先收集整棵子树，把其中所有文件统一软删除，再删除根节点；子文件夹靠外键级联删除。对象本体在事务提交后尽力清理，清理失败只记日志，不回滚元数据。

## 权限模型

权限校验分两层：

1. **功能级**：`file:own` 或 `file:manage`，决定能否进入某个页面 / 调用某个 Action。
2. **行级**：`canAccessFile()` 判断 `canManage || file.ownerId === user.id`，决定能否操作某条记录。

管理员视图里的「替用户操作」通过额外参数 `ownerId` 实现：

- 只有 `file:manage` 才能把 `ownerId` 指向别人。
- 目标的文件夹、文件都按该 `ownerId` 校验，避免跨用户挂载。
- 上传和新建的归属写入目标用户。

<Callout type="warn" title="不要把 ownerId 当作信任输入">
`ownerId` 来自客户端参数。`resolveOwner()` 先校验 `file:manage` 和目标用户是否存在，再写入数据库；没有这一步就变成了越权写。
</Callout>

## 查询与分页

`listFilePage()` 一次返回：文件分页结果、当前目录的子文件夹、面包屑和归一的查询状态。

关键约束：

- 每页 20 条，先 `count` 再取当前页，并把 `page` 夹在 `[1, pageCount]` 范围内。
- 排序都带 `id` 作为次级排序，保证分页边界稳定。
- 有搜索词时跨整个属主范围查找（文件按名称，文件夹按名称），否则只看当前目录。
- 查询参数（`q`、`sort`、`dir`、`page`、`folder`、`owner`）都在 `parseFileListState()` 里收敛，非法值回落到默认值，不会直接进 Prisma。
- `folder` 不属于当前用户或已被删除时，按根目录处理，而不是返回空列表。

## 安全边界

| 风险 | 处理 |
| --- | --- |
| 伪造文件大小 | `completeUpload` 以 `HeadObject` 结果为准 |
| 超大文件 | 200 MB 上限，超限删除对象并软删除记录 |
| 跨用户访问 | 每个 Action 都做行级归属校验，越权返回 `not_found` |
| 预签名被复用 | 15 分钟有效期，且只对单个对象键有效 |
| 对象键泄漏 | 键含随机 UUID，且 bucket 私有，只能通过预签名访问 |
| 文件名注入 | 键只使用清洗后的字符，显示名单独存储 |

## 已知限制

- 单文件超过 5 GB 需要 multipart 上传，目前未实现。
- 预签名 PUT 不能强制 `Content-Length`，只能在上传完成后校验。
- 没有病毒扫描、版本管理和回收站；软删除的记录目前只能通过数据库恢复。
- `PENDING` 记录如果客户端中途关闭页面，会留在表里；列表页会提示「上传未完成」并支持一键重试确认（每次最多 20 条），但定时清理任务仍未实现。
- 列表最多展示当前目录 20 条文件；文件夹不参与分页，始终全部展示。
