## Requirements

- Node.js 22.20 or newer (required by the `skills` CLI)
- Bun 1.2 or newer (`bun.lock` uses the text format)
- A PostgreSQL database
- A Logto application (required for local development too)
- A RustFS (S3-compatible) instance with a private bucket and CORS configured

## Setup

<Steps>

<Step>
### Install dependencies

```bash
bun ci
```

`bun ci` installs exactly what `bun.lock` specifies and never rewrites the lockfile. If the lockfile and `package.json` are out of sync, installation fails instead of silently changing the dependency tree.

</Step>

<Step>
### Install Skills (optional)

This step only controls which skill packs the agent can use. Skipping it does not affect starting or building the app.

To restore the skill packs in `skills-lock.json`:

```bash
bunx skills experimental_install
```

This command reads `skills-lock.json` and restores the Agent Skills into `.agents/skills/`. It does not install npm dependencies, so run it after dependencies are installed.

To use the project's own `browser-screenshot` skill, also run (optional):

```bash
bun run browser:install
```

This downloads Playwright's Chromium (~150 MB) once per machine. The skill itself is committed with the repo and needs no installation. See [Skills](/en/docs/skills) for details.

</Step>

<Step>
### Configure environment variables

The project loads `.env.<NODE_ENV>`, so local development uses `.env.development`. Start from the example file:

```bash
cp .env.example .env.development
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env.development
```

Then fill in the real database and Logto values:

```ini
DATABASE_URL=postgresql://user:password@localhost:5432/hucky
# 本地开发可以填同一个地址
MIGRATE_DATABASE_URL=postgresql://user:password@localhost:5432/hucky

LOGTO_ENDPOINT=https://your-tenant.logto.app
LOGTO_APP_ID=your-app-id
LOGTO_APP_SECRET=your-app-secret
LOGTO_BASE_URL=http://localhost:3000
LOGTO_COOKIE_SECRET=a-long-random-string
BOOTSTRAP_ADMIN_EMAILS=you@example.com

# RustFS (S3-compatible object storage)
RUSTFS_ENDPOINT=https://s3.example.com
RUSTFS_ACCESS_KEY=your-access-key
RUSTFS_SECRET_KEY=your-secret-key
RUSTFS_BUCKET=your-bucket
```

`DATABASE_URL` is used by the application at runtime; in production it should be the managed database's pooled connection string. `MIGRATE_DATABASE_URL` is only for migrations, seeding, and Prisma Studio, and must be a direct connection. In local development both can use the same value.

`LOGTO_BASE_URL` is the app's own URL; Logto redirects back here. `LOGTO_COOKIE_SECRET` must be at least 32 characters and should be strongly random in production. `.env.example` is committed to Git; real `.env*` files are not. See [Environment variables](/en/docs/infrastructure/environment-variables) for details.

`BOOTSTRAP_ADMIN_EMAILS` bootstraps the first deployment: while the system has no administrator, these verified emails receive the `admin` role on sign-in. Once an administrator exists, the variable has no effect and can be kept or removed.

`RUSTFS_*` powers the file module: `RUSTFS_ENDPOINT` must be an S3 API address the browser can reach directly (usually port 9000, not the 9001 console), the bucket must be private, and CORS must allow `PUT`, `GET`, and `HEAD`. The region is fixed to `us-east-1` and is not configurable. See [File storage](/en/docs/files).

</Step>

<Step>
### Initialize the database

```bash
bunx prisma generate
bun run db:setup
```

`prisma generate` writes the client to `lib/generated/prisma`. `db:setup` generates the client, runs `prisma migrate deploy`, and then the idempotent RBAC seed, which creates the built-in roles and permissions. Use `bunx prisma migrate dev` when you are developing new migrations. Use `bunx prisma studio` to browse data. See [Prisma database](/en/docs/prisma) for the schema, PostgreSQL setup, and migration workflow.

</Step>

<Step>
### Start the dev server

```bash
bun dev
```

Open `http://localhost:3000`; you will be redirected to the default locale `/zh`.

</Step>

</Steps>

## Scripts

| Command | Purpose |
| --- | --- |
| `bun ci` | Install from `bun.lock` (CI / fresh checkout) |
| `bun install` | Install dependencies and update `bun.lock` |
| `bun dev` | Start the dev server |
| `bun run build` | Production build |
| `bun start` | Run the production build |
| `bun run lint` | Biome checks |
| `bun run format` | Format with Biome |
| `bun run screenshot` | Capture a page with Playwright (requires Chromium) |
| `bun run browser:install` | Download Playwright's Chromium (once per machine) |
| `bun run db:setup` | Generate the client, apply migrations, and sync RBAC seed data |
| `bun run db:seed` | Sync RBAC seed data only (idempotent) |

## Auth and route protection

`proxy.ts` does two things: it adds the locale prefix via next-intl, then verifies the local session cookie.

- Public routes: `/`, `/login`, `/docs`
- Everything else redirects to `/<locale>/login?next=<original path>` when signed out

When you add a public page, update `publicRoutes` in `proxy.ts` too, or it will be treated as protected.

<Callout type="warn" title="New docs pages need no routing changes">
`/docs` is already public, so any new page under `content/docs` is reachable. Mounting docs at a different path means re-checking `publicRoutes`.
</Callout>
