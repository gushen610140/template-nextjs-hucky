This project delegates authentication entirely to Logto. Locally it keeps only three things:

- **`User`**: profile and authorization relations, with no password.
- **`Session`**: the app's own opaque session that decides whether a request is signed in.
- **RBAC**: roles and permissions, enforced by business code.

There is no local email/password login and no local registration endpoint. Every user enters through Logto.

## The only identity entry

| Item | Description |
| --- | --- |
| Sign-in entry | `Continue with Logto` on the login page |
| Credentials | Fully managed by Logto (password, social, MFA, ...) |
| Account source | Created or bound during the Logto callback |
| Session | Issued by this app after a successful callback |

Logto answers "who is this person"; the app answers "what may this person do". Business code does not need to know how the user signed in at Logto.

## Account linking rules

`lib/logto-user.ts` uses Logto's `sub` as the stable link:

1. A user with the same `logtoSub` already exists: sync `name`, `avatarUrl`, and the verified email.
2. No binding yet, but a legacy local account has the same email: bind `logtoSub` once and keep its roles and business data.
3. Neither exists: create a new local user.
4. No verified email: use `<sub>@logto.local` as a placeholder so it cannot collide with a real email.

<Callout type="warn" title="Only trust verified emails">
An unverified Logto email must not be used to bind a legacy account, or an attacker could enter someone else's email and take over the local account. The current code only uses the real email for a one-time bind when `email_verified === true`.
</Callout>

Email is just profile data. Changing it in Logto does not break the local account, because the link is the stable `sub`.

## Session model

Local sessions use an opaque token:

- The browser holds a random token in an httpOnly cookie.
- The database stores only `sha256(token)` in `Session.tokenHash`.
- `proxy.ts` looks up the session and user on protected requests.
- Expired sessions and disabled users are rejected and their sessions are deleted.
- Logout deletes the local session and clears the Logto SDK cookie.

See [Sessions and route protection](./session) for details.

## Current limits

- There is no local registration, password, code, or password-reset flow; Logto owns all of them.
- There is no UI to inspect or unlink a Logto identity.
- RBAC tables exist, but there is no admin UI or authorization API yet; business code must enforce permissions.
- There is no login rate limiting, audit log, or MFA; configure these in Logto first. See [Evolution](./evolution) for incremental upgrades.
