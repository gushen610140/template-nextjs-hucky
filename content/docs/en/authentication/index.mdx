The project supports two identity entry points:

- **Email + password**: handled entirely by the local database and sessions.
- **Logto**: OIDC sign-in, mapped to a local `User`.

Both entry points end up in the same `User` table and the same local session system. The core rule is: **one email maps to one local user**.

## Two sign-in paths

| Path | Entry | Credential | Account source |
| --- | --- | --- | --- |
| Email/password | `/login` form | Email + bcrypt hash | Local registration |
| Logto | `Continue with Logto` | Logto OIDC | Created or merged in callback |

Both paths call `createSession(user.id)` and write the same httpOnly cookie. Application code does not need to know which provider was used.

## Account linking rules

`lib/logto-user.ts` maps Logto claims to a local user:

1. If Logto returns a **verified email**, use that email to find the local user.
2. If found, update `name` and `avatarUrl`, keep the local `passwordHash`, and allow email/password login to continue.
3. If not found, create a new local user.
4. If there is no verified email, use `<logto-sub>@logto.local` as a placeholder email so an unverified email cannot be merged into an existing account.

<Callout type="warn" title="Only trust verified emails">
An unverified Logto email must not be used for account merging. Otherwise an attacker could enter someone else's email in Logto and take over the local account. The current code only uses the real email when `email_verified === true`.
</Callout>

## Session model

Local sessions use an opaque token:

- The browser holds a random token in an httpOnly cookie.
- The database stores only `sha256(token)` in `Session.tokenHash`.
- `proxy.ts` looks up the session and user on protected requests.
- Expired sessions and disabled users are rejected and their sessions are deleted.
- Logout deletes the local session and clears the Logto SDK cookie.

## Current limits

- Local **code login is disabled**. There is no email delivery service, so the placeholder that accepted any six-digit code was removed. Passwordless login should go through Logto or a real OTP implementation.
- No email verification. The email entered at registration is trusted; production should add verification.
- RBAC tables exist, but there is no admin UI or authorization API yet; business code must enforce permissions.
- No login rate limiting, audit log, or MFA. See [Evolution](./evolution).
