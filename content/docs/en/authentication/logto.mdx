Logto is the only identity provider in this project. It owns the sign-in UI and identity verification; the app still owns its `User` table and local session.

## Configuration

Set these in `.env.development` / `.env.production`:

```ini
LOGTO_ENDPOINT=https://your-tenant.logto.app
LOGTO_APP_ID=your-app-id
LOGTO_APP_SECRET=your-app-secret
LOGTO_BASE_URL=http://localhost:3000
LOGTO_COOKIE_SECRET=a-long-random-string
```

- `LOGTO_BASE_URL` must match the site part of the Redirect URI registered in Logto.
- Register this Redirect URI:

```text
http://localhost:3000/api/auth/callback
```

Use the production domain in production. The callback lives under `/api`, so it bypasses the next-intl middleware and needs no locale prefix.

## Sign-in flow

1. The user clicks `Continue with Logto`.
2. The browser goes to `/api/auth/logto?next=...`.
3. `next` is stored in a short-lived `logto_next` httpOnly cookie.
4. The Logto SDK redirects to the authorization page.
5. Logto redirects back to `/api/auth/callback?code=...&state=...`.
6. `handleSignIn` verifies `state`, exchanges the code for tokens, and stores them in the Logto SDK's encrypted cookie.
7. `getLogtoContext` reads the ID token claims.
8. `upsertLogtoUser` maps claims to a local `User`.
9. A local session is created and the `session` cookie is written.
10. The user returns to `logto_next` or the default locale dashboard.

## Claims mapping

Rules in `lib/logto-user.ts`:

| Case | Local behavior |
| --- | --- |
| Same `logtoSub` already exists | Sync `name`, `avatarUrl`, and the verified email |
| Not bound, but a legacy account has the same email | Bind `logtoSub` once and keep roles and business data |
| Neither exists | Create a new `User` |
| No verified email | Use `<sub>@logto.local` as a placeholder |
| Concurrent callbacks create at once | Catch `P2002` and re-read the created account |
| Email already used by another Logto identity | Fall back to the placeholder email instead of overwriting |

### Why `sub` instead of email

Logto's `sub` never changes for a user, while the email can be edited. Keying on email would make an email change look like a new user, or even merge into another account with that email. The unique `logtoSub` column avoids both.

### Why use a placeholder email

Some Logto instances only enable username sign-in and provide no verified email. Using an unverified email for matching could let someone take over an existing local account. `<sub>@logto.local` is stable for the Logto identity and cannot collide with a real email.

<Callout type="warn" title="Do not trust unverified email">
Only `email_verified === true` may participate in the one-time bind to a legacy account. Confirm that Logto has completed verification before changing this rule.
</Callout>

## Logout

`POST /api/auth/logout`:

1. Deletes the local `Session`.
2. Clears the `session` cookie.
3. Clears the Logto SDK cookie `logto_<appId>`.

If the user still has a Logto SSO session, clicking Logto again may return without a password prompt. That is Logto SSO behavior; it does not mean the local session is still valid.

## Current limits

- There is no UI to inspect or unlink a Logto identity.
- One local user can bind only one Logto identity today. If you need multiple identities, add an `AuthIdentity` table; see [Evolution](./evolution).
- Callback errors all redirect to `/login?error=logto` without finer error codes.
- Logto access tokens are not cached locally. When calling the Account or Management API, request one explicitly with `getAccessToken` / `getAccessTokenRSC`.

## Debug checklist

- Is the Redirect URI in Logto exactly `<LOGTO_BASE_URL>/api/auth/callback`?
- Does `LOGTO_BASE_URL` match the browser URL?
- Is `LOGTO_COOKIE_SECRET` at least 32 characters?
- Does the user actually have a verified email?
- Does a local user with that email or `logtoSub` already exist, and is it active?
