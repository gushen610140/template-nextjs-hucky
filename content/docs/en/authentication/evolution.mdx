---
title: Evolution and extensions
description: Move from a single identity to multiple identities, audit, and stronger sessions
---

The current design fits a basic "one Logto identity, one local user" scenario. The following upgrades are ordered by risk and value.

## Current boundaries

| Capability | State | Risk |
| --- | --- | --- |
| Logto sign-in | Implemented | One local user can bind one Logto identity |
| Local password / code | Removed | Auth policy must be configured in Logto |
| RBAC tables | Created | No authorization API, admin UI, or seed |
| Session | Implemented | No "sign out everywhere" or audit |
| Disabled users | Implemented | Login and old sessions are rejected |
| Email changes | Handled by `logtoSub` | Email is profile data and does not affect linking |

## 1. Support multiple identities per user

Today `User.logtoSub` stores exactly one Logto identity. If you later add a second IdP, or let one user link several sign-in methods, add an identity table:

```prisma
model AuthIdentity {
  id                String   @id @default(cuid())
  provider          String   // "logto" or another IdP
  providerAccountId String   // stable user ID at that IdP
  userId            String
  email             String?
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([provider, providerAccountId])
  @@index([userId])
  @@index([email])
}
```

Add the reverse relation to `User`:

```prisma
identities AuthIdentity[]
```

Rollout order:

1. Add nullable structures without changing sign-in.
2. Backfill `AuthIdentity` during login.
3. Prefer `provider + providerAccountId` for lookup.
4. Fall back to a verified email only when no identity exists.
5. Decide later whether `User.logtoSub` can be removed.

<Callout type="warn" title="Never merge unverified emails">
Email merging must require `email_verified === true`. Otherwise anyone can put a victim's email into a third-party IdP and take over the local account.
</Callout>

## 2. Code and passwordless login

Authentication belongs to Logto. Prefer enabling email codes, social sign-in, or MFA in the Logto console instead of rebuilding them locally.

If you do need a local OTP, a correct implementation requires:

- Server-generated OTP, never client-generated.
- Only a hash stored in the database.
- Short expiry, such as 5–10 minutes.
- Attempt limits and invalidation after too many failures.
- Rate limits by email, IP, and device.
- One-time use.
- No account-existence leakage on send failures.

Possible model:

```prisma
model VerificationCode {
  id        String   @id @default(cuid())
  email     String
  codeHash  String
  purpose   String
  attempts  Int      @default(0)
  expiresAt DateTime
  createdAt DateTime @default(now())

  @@index([email, purpose])
  @@index([expiresAt])
}
```

Do not restore the "any six-digit code passes" placeholder.

## 3. Email verification

Email ownership is verified by Logto; the app only reads `email_verified`. If the business needs a stronger proof, enable verification in Logto first, then decide whether `User.emailVerifiedAt` should gate sensitive actions.

## 4. Session hardening

Consider:

- Rotate the session token on login or privilege elevation.
- "Sign out everywhere" by deleting all sessions for a `userId`.
- Periodically clean expired sessions and add an `expiresAt` index.
- Record login time, IP, and User-Agent for a session list.
- Require re-authentication for sensitive actions.

`getSessionUser` already cleans expired or disabled sessions and selects only safe fields. Do not start returning internal link fields with it.

## 5. Rate limiting and audit

Configure authentication rate limits in Logto first. On the app side, still record:

- Audit logs for login success, failure, logout, and role changes.
- Alerts for the same account signing in from many locations in a short window.
- Re-confirmation for sensitive actions.

Never log session tokens or any IdP credentials.

## 6. RBAC management

Only tables exist today. Recommended order:

1. Seed roles and permissions.
2. Add `lib/authz.ts`.
3. Add role management APIs.
4. Add user-role assignment UI.
5. Add audit trails and cache invalidation.

- [ ] Run `bunx prisma generate`
- [ ] Update types in `lib/session.ts` and `lib/logto-user.ts`
- [ ] Add tests for failure paths on every new auth route
- [ ] Verify `LOGTO_BASE_URL` and callback URLs in production
- [ ] Confirm no real secrets are committed to `.env.example`
- [ ] Verify disabled users cannot log in or reuse old sessions
