Logto owns authentication; this app only owns sessions and authorization. After a successful Logto sign-in, the callback route maps the Logto identity to a local `User` and issues a local opaque session.

## Creating a session after sign-in

`app/api/auth/callback/route.ts` performs the OIDC callback, then:

1. Calls `upsertLogtoUser(claims)` to find or create the local user.
2. Checks `user.isActive`; disabled users are sent back to the login page.
3. Calls `createSession(user.id)` to generate a random token.
4. Writes the raw token to the httpOnly `session` cookie and stores only its hash in the database.
5. Redirects to `logto_next`, or to the default-locale dashboard.

## Session design

Sessions use an opaque token: the browser holds a random value, and the database stores only its hash.

```ts
// lib/session.ts
const token = randomBytes(32).toString("base64url");
const tokenHash = createHash("sha256").update(token).digest("hex");

await prisma.session.create({
  data: {
    tokenHash,
    userId,
    expiresAt: new Date(Date.now() + SESSION_DURATION_MS),
  },
});
```

If the database leaks, the attacker only gets `tokenHash` and cannot recover the raw cookie value. Sessions last 7 days by default.

Cookie options:

```ts
{
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "lax",
  path: "/",
  maxAge: 7 * 24 * 60 * 60,
}
```

## Route protection

Validation has two layers: `proxy.ts` performs an optimistic check without touching the database, and the data layer performs the authoritative one.

`proxy.ts` runs after next-intl handles the locale prefix:

1. Public routes pass through: `/`, `/login`, `/docs`.
2. Protected routes only check that the `session` cookie exists and looks like a token minted by this app.
3. A missing or malformed cookie redirects to `/<locale>/login?next=<original path>`.
4. The original pathname is forwarded in the `x-pathname` request header for the data layer to build the return URL.

The real session check runs in the protected segment's layout:

```tsx
// app/[locale]/dashboard/layout.tsx
import { requireUser } from "@/lib/auth";

await requireUser();
```

`requireUser()` reads the token from the cookie, calls `getSessionUser(token)` to look up the database, and validates the expiry and `user.isActive`. It redirects to `/<locale>/login?next=<x-pathname>` when the session is invalid, otherwise it returns the user without `logtoSub`.

`getCurrentUser()` uses React `cache` for per-request deduplication: layout, page, and components that call it during one render only hit the database once.

<Callout type="warn" title="The proxy is not a security boundary">
A forged cookie with the right shape passes the optimistic check in `proxy.ts`. Every page, Server Action, and Route Handler that needs a user must call `requireUser()` or `getCurrentUser()`.
</Callout>

`next` must start with `/` and must not start with `//`, which prevents open redirects. After sign-in, the app returns to `next` when it is a safe in-site path.

## Endpoints

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/api/auth/logto` | `GET` | Start Logto sign-in |
| `/api/auth/callback` | `GET` | Finish the OIDC callback and create a session |
| `/api/auth/logout` | `POST` | Delete the current session and clear cookies |
| `/api/auth/me` | `GET` | Read the current user |

## Security notes

- The session token lives only in an httpOnly cookie. Do not read it in the browser or put it in `localStorage`.
- Production must use HTTPS for the `secure` cookie flag to take effect.
- Logout deletes the local session but does not revoke the global Logto SSO session. Clicking Logto again may return without a password prompt; that is expected.
- Disabling a user in Logto does not immediately invalidate existing local sessions; they can live for up to 7 days. For immediate lockout, also set `User.isActive = false`, or shorten the session lifetime.
- There is no "sign out everywhere" yet. It is a `deleteMany` on `Session` by `userId`; see [Evolution](./evolution).
