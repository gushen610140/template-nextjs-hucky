`feishu-pm` is a project-level OpenCode plugin for customer and team collaboration: it watches local `main` commits, captures pages, and pushes updates; it also receives @bot messages in customer groups and files them as requirement documents.

It cannot drive OpenCode. The developer-facing control bot is a separate global plugin named `feishu-bridge`; the two must use **different Feishu apps**.

```text
new main commit
  → poll refs/heads/main every 20 seconds
  → reuse or start the dev server
  → Playwright captures configured pages
  → commit summary + screenshots
  → configured Feishu group / DM
```

```text
customer @-mentions the bot in a group
  → long connection receives the message
  → AI drafts a structured requirement
  → writes requirements/<time>-<title>.md
  → replies with the file path
```

## How it works

- The first start records the current HEAD as a baseline and does not backfill old commits.
- Each new commit is summarized by OpenCode's AI in 2-4 customer-facing sentences; failures or timeouts fall back to the commit title.
- Screenshots live in `.screenshots/commits/` and are overwritten each run.
- On failure it sends a text error and writes to `debug.log`.
- A Feishu long connection receives group messages, but only allowlisted chats with @bot text are processed.

## Control and status

The `FEISHU-PM` sidebar block shows `watching` / `off`, the page count, and the latest commit. TUI commands:

| Command | Effect |
| --- | --- |
| `/feishu-pm-status` | Toggle state, target, pages, latest commit, and error |
| `/feishu-pm-on` | Enable and persist |
| `/feishu-pm-off` | Disable and persist |
| `/feishu-pm-restart` | Restart watching |
| `/feishu-pm-log` | Last 20 log lines |

Watching is enabled by default. `/feishu-pm-off` writes to plugin storage and stays off across restarts.

The developer control bot is a separate global plugin with the `/feishu-bridge-*` command prefix.

## Quick start

<Steps>

<Step>
### Create a customer app

Create a custom app on the Feishu Open Platform, enable the bot capability, add the send and group @-mention receive scopes, then publish a version. Do not reuse the developer control bot.

| Scope | Purpose |
| --- | --- |
| `im:message:send_as_bot` | Send text and images |
| `im:resource` | Upload screenshots |
| `im:message.group_at_msg:readonly` | Receive group messages that mention the bot |
| `im:chat:readonly` | List the bot's chats and read chat names |
| `contact:contact.base:readonly` | Resolve the sender name |

Subscribe to `im.message.receive_v1` over the long connection. No card callbacks or permission approvals are needed.

</Step>

<Step>
### Fill in configuration

Copy `.opencode/plugins/feishu-pm/.env.example` to `.env` and fill in the App ID, App Secret, and delivery target. `.env` is git-ignored.
</Step>

<Step>
### Install dependencies and Chromium

```powershell
npm install --prefix .opencode/plugins/feishu-pm
bun run browser:install
```

`browser:install` runs once per machine.
</Step>

<Step>
### Restart OpenCode

The plugin starts watching as soon as it loads; there is no `/feishu-on`. Commit to `main` and the summary and screenshots should arrive within 20 seconds.

</Step>

</Steps>

## Configuration

```bash
FEISHU_PM_APP_ID=cli_xxxxxxxx
FEISHU_PM_APP_SECRET=xxxxxxxx

# delivery target: one of the two
FEISHU_PM_NOTIFY_CHAT_ID=
FEISHU_PM_NOTIFY_OPEN_ID=

# optional
FEISHU_PM_ENABLED=1
FEISHU_PM_SUMMARY=1
FEISHU_PM_RECEIVE=1
FEISHU_PM_ALLOWED_CHAT_IDS=
FEISHU_PM_REQUIREMENTS_DIR=requirements
FEISHU_SCREENSHOT_PAGES=/,/docs,/login
FEISHU_SCREENSHOT_BASE=http://localhost:3000
FEISHU_SCREENSHOT_MATCH=Hucky
FEISHU_SCREENSHOT_POLL_MS=20000
```

| Variable | Required | Description |
| --- | --- | --- |
| `FEISHU_PM_APP_ID` | Yes | Customer app ID |
| `FEISHU_PM_APP_SECRET` | Yes | Customer app secret |
| `FEISHU_PM_NOTIFY_CHAT_ID` | one of two | Group or DM chat_id, preferred |
| `FEISHU_PM_NOTIFY_OPEN_ID` | one of two | DM user open_id |
| `FEISHU_PM_ENABLED` | No | Enabled by default; set to `0` to disable |
| `FEISHU_PM_SUMMARY` | No | Set to `0` to disable AI summaries |
| `FEISHU_PM_RECEIVE` | No | Set to `0` to disable group requirement intake |
| `FEISHU_PM_ALLOWED_CHAT_IDS` | No | Chats allowed to submit requirements; empty means only `FEISHU_PM_NOTIFY_CHAT_ID` |
| `FEISHU_PM_REQUIREMENTS_DIR` | No | Requirement directory, default `requirements` |
| `FEISHU_SCREENSHOT_PAGES` | No | Pages to capture; defaults to `/`, `/docs`, `/login` |
| `FEISHU_SCREENSHOT_BASE` | No | Dev or preview URL; defaults to `http://localhost:3000` |
| `FEISHU_SCREENSHOT_MATCH` | No | Text the page must contain to confirm it belongs to this project |
| `FEISHU_SCREENSHOT_POLL_MS` | No | Poll interval, default 20000, minimum 5000 |

Targets come only from configuration. Credentials, target, and toggles use the `FEISHU_PM_` prefix so they cannot collide with the global feishu-bridge in the same OpenCode process.

## Getting a chat_id

1. Add the bot to the customer group.
2. Call `GET /open-apis/im/v1/chats` in the Feishu API explorer (requires `im:chat:readonly`) and put the returned `chat_id` into `FEISHU_PM_NOTIFY_CHAT_ID`.
3. For a DM smoke test, you can use `FEISHU_PM_NOTIFY_OPEN_ID` first.

## Receiving customer requirements

1. A customer @-mentions the bot in a group with text.
2. Only chats in `FEISHU_PM_ALLOWED_CHAT_IDS` are processed; when empty, only `FEISHU_PM_NOTIFY_CHAT_ID` is accepted.
3. The AI drafts a fixed structure and writes it to `FEISHU_PM_REQUIREMENTS_DIR` (default `requirements`): `requirements/<YYYYMMDD-HHmmss>-<title>.md`.
4. The document has `source`, `chat_id`, `chat_name`, `sender_id`, `sender_name`, `message_id`, and `created_at` (local time) frontmatter, plus “Customer request / Requirements / Acceptance / Open questions”. Missing names fall back to ids.
5. The bot replies with the file path and title.

Security: customer text is passed to the model as data only; the prompt forbids following instructions inside it or calling tools. The plugin writes files into a fixed directory, and the model never touches the filesystem. Non-text messages get “text only for now”.

## Dev server and preview

- A reachable `FEISHU_SCREENSHOT_BASE` is reused and never shut down.
- If not reachable, nearby ports are checked for an existing project server and reused.
- Otherwise the plugin starts `next dev` and stops it after capturing.
- `next dev` allows only one instance per project; point `FEISHU_SCREENSHOT_BASE` at an existing instance on another port.
- Once a preview deployment exists, point `FEISHU_SCREENSHOT_BASE` at it so customers preview before accepting.

## Requirements

- The OpenCode server must stay running; stopping it stops the feed.
- Node.js, `bun`, and Playwright's Chromium are required.
- Capture uses `scripts/screenshot.mjs`; you can also run `bun run screenshot` manually.

## Logs

`.opencode/plugins/feishu-pm/debug.log`:

| Log | Meaning |
| --- | --- |
| `watcher started` | Watching has started |
| `screenshot: baseline recorded` | First start recorded the baseline; expected |
| `screenshot: sent` | Delivery succeeded |
| `screenshot: no feishu target` | Delivery target missing |
| `screenshot: FAILED` | Capture or delivery failed |
| `dev server 启动失败` | A `next dev` instance exists or ports conflict |
| `receiver ready` | Group message long connection is up |
| `requirement saved` | Requirement document written |
| `requirement timeout` | AI drafting exceeded 90 seconds |
| `requirement ignored: chat not allowed` | Chat not allowlisted, ignored |
| `missing FEISHU_PM_APP_ID / FEISHU_PM_APP_SECRET` | Credentials are missing |

## Roadmap

- **Fixed customer group feed**: per-group content, cadence, and quiet hours.
- **Preview acceptance**: send screenshots with a preview link and let customers confirm in the group.
- **Requirement status sync**: connect requirement documents to the todo list and track delivery.
- **Collaboration loop**: developers confirm requirements, progress, and acceptance with customers through Feishu and AI.

These are not implemented yet; this page will be updated as they land.

## Limitations

- Feishu and Lark only; no WeCom or DingTalk.
- Only local commits on `main` are covered; remote updates and `git push` are not watched.
- The delivery target must be configured in advance; there is no auto-discovery from messages.
- It depends on a running OpenCode server.
