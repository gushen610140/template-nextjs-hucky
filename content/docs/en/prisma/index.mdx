The project uses **Prisma 7** as the ORM for PostgreSQL. Prisma covers three concerns:

- Describing the data model in `prisma/schema.prisma`
- Managing schema changes through `prisma/migrations`
- Generating a type-safe Prisma Client for server-side queries

The database is PostgreSQL, the driver adapter is `@prisma/adapter-pg`, and the underlying connection pool comes from `pg`.

## File layout

| Path | Purpose |
| --- | --- |
| `prisma/schema.prisma` | Models, relations, indexes, and generator configuration |
| `prisma/migrations/` | Ordered SQL migrations; must be committed to Git |
| `prisma.config.ts` | Prisma CLI config that loads the environment file and `MIGRATE_DATABASE_URL` (falling back to `DATABASE_URL`) |
| `lib/prisma-client.ts` | Shared Prisma Client factory used by runtime and seed |
| `lib/prisma.ts` | The single runtime Prisma Client instance, reading `DATABASE_URL` |
| `lib/generated/prisma/` | Generated client; ignored by Git |
| `lib/session.ts` | Creates, reads, and deletes sessions with Prisma |
| `lib/logto-user.ts` | Maps a Logto identity to the local `User` table |
| `app/api/auth/` | Sign-in start, callback, logout, and current-user endpoints |
| `app/api/auth/callback/route.ts` | Logto callback that writes the local user and session |

`lib/generated/prisma` is not tracked. Regenerate it after a fresh clone, a branch switch, or any schema change.

## From clone to first query

<Steps>

<Step>
### Install dependencies

```bash
bun ci
```

This installs the `prisma` CLI, `@prisma/client`, `@prisma/adapter-pg`, and `pg`.
</Step>

<Step>
### Configure the database connection

Copy the example file and fill in the database connection strings. In local development both can use the same value:

```bash
cp .env.example .env.development
```

```ini
DATABASE_URL=postgresql://user:password@localhost:5432/hucky
MIGRATE_DATABASE_URL=postgresql://user:password@localhost:5432/hucky
```

`DATABASE_URL` is used by the application runtime; `MIGRATE_DATABASE_URL` is used by migrations and seeding and should point at a direct connection in production. See [Environment variables](/en/docs/infrastructure/environment-variables) for the full environment-file rules. If you do not have a database yet, start with [PostgreSQL](/en/docs/prisma/postgresql).
</Step>

<Step>
### Generate the client and apply migrations

```bash
bunx prisma generate
bunx prisma migrate dev
```

`generate` writes the client to `lib/generated/prisma`. `migrate dev` applies pending migrations from `prisma/migrations`; on a fresh database it creates the tables in order.

Do not run `migrate dev` in production. Use `bunx prisma migrate deploy` there; see [Migrations](/en/docs/prisma/migrations).
</Step>

<Step>
### Start the app

```bash
bun dev
```

Session checks and the Logto callback both reach the database through `lib/prisma.ts`.
</Step>

</Steps>

## How it works

A query travels from configuration to SQL roughly like this:

```text
prisma.config.ts
  └─ dotenv reads .env.<NODE_ENV>
       └─ MIGRATE_DATABASE_URL (falls back to DATABASE_URL)
            └─ prisma migrate / db seed / studio

prisma/schema.prisma
  └─ bunx prisma generate
       └─ lib/generated/prisma (type-safe client code)

lib/prisma.ts
  └─ createPrismaClient(DATABASE_URL)
       └─ new PrismaPg({ connectionString })
            └─ new PrismaClient({ adapter })
                 └─ pg Pool
                      └─ PostgreSQL
```

Application code only depends on the `prisma` export from `lib/prisma.ts`. It does three things:

1. Reads the runtime connection string from `process.env.DATABASE_URL`.
2. Creates a PostgreSQL driver adapter through the factory in `lib/prisma-client.ts` and `PrismaPg`.
3. Stores the instance on `globalThis` in development so Next.js hot reload does not create a new pool on every change.

Migrations and seeding bypass this singleton: `prisma.config.ts` and `prisma/seed.ts` use `MIGRATE_DATABASE_URL ?? DATABASE_URL` so they go through a direct connection.

## Development workflow

Use this order when changing database-backed features:

1. Edit `prisma/schema.prisma`.
2. Run `bunx prisma format` and `bunx prisma validate`.
3. Run `bunx prisma migrate dev --name <change-name>` to create and apply a migration.
4. Inspect the generated `migration.sql`.
5. Run `bunx prisma generate` to refresh client types.
6. Update the application code and run tests.
7. Commit the schema, migration, and code together.

<Callout type="warn" title="Do not edit database tables directly">
Manually adding columns, dropping tables, or changing types in PostgreSQL creates drift between the database and the migration history. A later `migrate dev` may ask to reset the database. Always start schema changes from `schema.prisma`.
</Callout>

## Conventions

- Commit migration files; do not commit `lib/generated/prisma`.
- Never edit a migration that has already been applied.
- Use `migrate dev` locally and `migrate deploy` in production.
- `db push` is acceptable for throwaway prototypes, but real data should use migrations.
- Use `bunx prisma` in this repository, not `npx prisma`, to avoid mixing package managers.
- The `prisma` CLI is a dev dependency; `bunx prisma` uses the project-local version, not a global install.
