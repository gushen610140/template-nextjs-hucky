`prisma/schema.prisma` is the single source of truth for the data model. Tables are created by migrations; application code accesses them through Prisma Client, never by building DDL by hand.

## Schema structure

The generator and datasource are defined at the top of the file:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../lib/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

- `provider = "prisma-client"` generates TypeScript into `lib/generated/prisma`.
- `datasource db` only declares the database type; the actual URL comes from `datasource.url` in `prisma.config.ts`.
- The generated client is ignored by `.gitignore` and must not be edited manually.

## Models

| Model | Purpose |
| --- | --- |
| `User` | Local profile, Logto link, active flag, and timestamps |
| `Role` | Roles such as admin or editor |
| `Permission` | Coarse-grained permissions such as `basic:manage` or `ai:manage` |
| `UserRole` | Many-to-many join table between users and roles |
| `RolePermission` | Many-to-many join table between roles and permissions |
| `Session` | Opaque server-side sessions with token hashes and expiry |
| `FileObject` | File metadata: object key, size, status, owner, and folder |
| `FileFolder` | Virtual folder tree; files reference it through `folderId` |

### User

```prisma
model User {
  id           String   @id @default(cuid())
  logtoSub     String?  @unique
  email        String   @unique
  name         String?
  avatarUrl    String?
  isActive     Boolean  @default(true)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  roles    UserRole[]
  sessions Session[]
  files    FileObject[]
  folders  FileFolder[]
}
```

Design notes:

- `id` uses `cuid()` instead of exposing auto-increment IDs.
- `logtoSub` is Logto's stable user identifier and the only identity link.
- `email` is unique and comes from Logto claims. Users can change it in Logto, so it does not participate in identity linking.
- `name` and `avatarUrl` are optional and synced from Logto claims.
- `isActive` marks disabled accounts. Session validation and the Logto callback reject inactive users.
- `updatedAt` is maintained by Prisma on update.

### Session

```prisma
model Session {
  id        String   @id @default(cuid())
  tokenHash String   @unique
  userId    String
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}
```

Sessions use an opaque-token design:

1. The server generates a random token and stores only the raw value in an httpOnly cookie.
2. The database stores `sha256(token)` in `tokenHash`.
3. Every request looks up the session by `tokenHash` and checks `expiresAt`.
4. Expired and inactive-user sessions are deleted when read; logout deletes by token hash.
5. `@@index([userId])` supports cleanup by user.

<Callout title="Session to User relation">
`Session` is many-to-one with `User`. `onDelete: Cascade` removes all sessions when a user is deleted, so no orphaned login state remains.
</Callout>

## Roles and permissions

Roles and permissions use explicit many-to-many join tables:

```prisma
model UserRole {
  userId String
  roleId String

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)
  role Role @relation(fields: [roleId], references: [id], onDelete: Cascade)

  @@id([userId, roleId])
}

model RolePermission {
  roleId       String
  permissionId String

  role       Role       @relation(fields: [roleId], references: [id], onDelete: Cascade)
  permission Permission @relation(fields: [permissionId], references: [id], onDelete: Cascade)

  @@id([roleId, permissionId])
}
```

Relationship diagram:

```text
User ──< UserRole >── Role ──< RolePermission >── Permission
  │
  └──< Session
```

- The composite primary key `@@id([userId, roleId])` prevents assigning the same role twice.
- Both sides use `onDelete: Cascade`, so deleting a role or permission cleans up its links.
- `Permission.name` is unique and is a stable identifier for authorization checks.
- `Permission.module` groups permissions by area, such as `user`, `post`, or `settings`.

## Files and folders

File bodies live in object storage; the database only holds metadata:

```prisma
enum FileStatus {
  PENDING
  READY
  DELETED
}

model FileObject {
  id        String     @id @default(cuid())
  ownerId   String
  folderId  String?
  bucket    String
  key       String     @unique
  name      String
  mimeType  String
  size      BigInt
  etag      String?
  status    FileStatus @default(PENDING)
  createdAt DateTime   @default(now())
  updatedAt DateTime   @updatedAt
  deletedAt DateTime?

  owner  User        @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  folder FileFolder? @relation(fields: [folderId], references: [id], onDelete: SetNull)

  @@index([ownerId, status, createdAt(sort: Desc)])
  @@index([ownerId, folderId, status, createdAt(sort: Desc)])
  @@index([status, createdAt(sort: Desc)])
}

model FileFolder {
  id        String   @id @default(cuid())
  ownerId   String
  parentId  String?
  name      String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  owner    User         @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  parent   FileFolder?  @relation("FolderTree", fields: [parentId], references: [id], onDelete: Cascade)
  children FileFolder[] @relation("FolderTree")
  files    FileObject[]

  @@index([ownerId, parentId, createdAt(sort: Desc)])
}
```

```text
User ──< FileObject >── FileFolder ──< FileFolder (self tree)
```

Design notes:

- `status` implements soft deletion; `deletedAt` records when it happened and lists filter on `status`.
- `size` uses `BigInt` so files over 2 GB do not overflow.
- `key` is the unique object key in the bucket; `name` is what users see. They are decoupled, so renaming never moves an object.
- `folder` uses `onDelete: SetNull`: after a folder is hard-deleted, already soft-deleted file rows fall back to the root instead of losing metadata.
- `FileFolder.parent` cascades, so deleting a parent removes child folders. Files must be soft-deleted by application code first.
- `ownerId` appears on both models; `(ownerId, folderId, status, createdAt)` supports listing by owner, folder, and status.

See [File storage](/en/docs/files/design) for the full deletion and permission semantics.

## Field and index conventions

- Use PascalCase for models and camelCase for fields. Prisma quotes these identifiers in SQL.
- To use snake_case in the database, add `@map` / `@@map`, but remember that this changes the actual column names and requires a migration.
- Evaluate `@@index` for columns used in `where`, `orderBy`, or relation lookups.
- Use `@unique` for business keys: `User.email`, `Role.name`, `Permission.name`, and `Session.tokenHash`.
- Be explicit about delete behavior. The current project cascades users, roles, permissions, and sessions.
- Use `DateTime` consistently; creation times use `@default(now())` and updates use `@updatedAt`.
- Store only hashes or irreversible digests for sensitive values. Never store plaintext tokens, passwords, or secrets.

## Changing the model

Updating `schema.prisma` is not the whole change. See [Migrations](/en/docs/prisma/migrations) for the full flow:

1. Edit the model.
2. `bunx prisma format`
3. `bunx prisma validate`
4. `bunx prisma migrate dev --name <change-name>`
5. `bunx prisma generate`
6. Update the code that uses the model

Do not add columns manually in the database and then update the schema; that leaves the migration history out of sync with reality.
